# 画布、画布 App、文档 App：关系与闭环状态

核验日期：2026-10-21。本报告针对本地代码与隔离测试，不等同于线上部署验收。

## 先看结论

**不是三个互相复制的产品，而是一个工作台、一个画布能力服务、一个独立文档服务。**

- 画布工作台：你看到的卡片、连线、文件和页签界面。
- 画布 App：把同一套画布能力以标准 API 对外提供，供 Agent、管理平台及其他 App 调用。不是另建一份画布数据。
- 文档 App：独立保存正文、提供编辑器；既可以单独使用，也可以被画布工作台挂载。

**已验证本地基础使用闭环；不能据此宣称生产多租户、离线同步和多人并发已全部闭环。**

## 一、谁负责什么

```text
画布工作台（用户界面）
├─ 画布视图 ──→ 画布 App / API ──→ 画布自己的存储
│                管卡片、位置、连线、画布实例与绑定索引
│
└─ 文档页签 / 卡片详情
     挂载文档 App 的同一个编辑器组件
                    │
                    └──→ 文档 App / API ──→ 文档自己的存储
                           管正文、文档名称、文档归档

卡片  ←── binding 关联 ──→  文档
画布预览正文和镜像文件     文档正文的权威存储
```

这里必须区分两种“保存”：

1. **文档已保存**：正文已经落进文档 App 的存储。
2. **画布已同步**：画布镜像文件与卡片预览也已经更新。

第一步成功不代表第二步一定成功。本轮已把两种状态分开，不能再用一个 HTTP 200 冒充全链路成功。

### 哪一份是正文真相？

- 已绑定的文档：正文真相在文档 App。
- 画布上的 `node.text` 和文件：用于显示、实时操作、快照的副本。
- 直接在卡片内编辑：视为向文档发起正文更新，同时先保存画布本地编辑。
- 文档服务未连接时：画布仍能保存和显示，但不能声称文档也已同步。
- 打开详情：读取文档正文，**不再擅自用画布副本覆盖文档**。若不一致，保留双方并提示。

## 二、各自是否闭环

| 对象 | 当前结论 | 已核验范围 |
|---|---|---|
| 画布工作台 + 画布 App | 本地画布基本闭环 | 状态、卡片操作、文件、绑定及租户门禁的服务端回归；既有 Web 全量回归 |
| 文档 App 独立使用 | 本地基础编辑闭环 | 真实浏览器：空列表 → 新建 → 编辑 → 自动保存 → 刷新重开 → 正文一致 → 返回列表 |
| 画布与文档在线互联 | 基础双向闭环 | 实际双进程 HTTP：建卡出生绑定、文档保存回写文件与卡片、跨租户拒绝、删除/归档行为 |
| 断网、重启后的自动补偿 | **未完整闭环** | 失败有状态和审计；尚无持久同步队列与自动冲突解决 |
| 同时多人编辑同一正文 | **未完整闭环** | 画布镜像有版本冲突保护；文档本体仍非带版本 CAS 的协同编辑系统 |
| Appwrite / 生产多租户 | **未验收** | 有本地隔离测试和云存储 mock；没有真实团队服务、云 schema 迁移和部署验收 |

文档 App 的生命周期 API 与独立壳的功能范围也不要混淆：API 有改名和归档门禁；本次浏览器验收只覆盖基础新建、编辑、保存与重开，没有宣称所有管理功能都有独立页面入口。

## 三、租户关系：App 共用，不等于数据共用

### 1. App 的可见范围

- `platform`：平台提供的能力，各团队可以发现和使用，例如统一的文档 App。
- `team`：某个团队自装的 App，其他团队不能发现或通过代理绕过限制调用。

### 2. 资产的归属

每个画布和文档仍有自己的团队归属。同一文档 App 内，A 团队与 B 团队的数据不应混在一起。

- 独立创建文档：属于当前请求团队。
- 从卡片创建文档：继承画布团队。
- 关联文档的识别键：**团队 + 画布 ID + 卡片 ID**，不能只认卡片 ID。
- 操作审计与用户级授权：使用实际编辑者，而不是一直冒用画布创建者。
- `local` 是开发时的默认团队，不是跨团队超级管理员。

### 3. 开发态隔离不等于生产认证

本地请求用团队/用户头进行上下文隔离。生产环境必须由可信身份适配器/网关注入，不能相信浏览器任意自报的团队。

- 画布管理面在本地无认证模式才保留 `local/local` 初始化操作员便利；有认证适配器或 token 时不能靠这个默认身份获得平台管理权。
- 文档启用 `DOC_REQUIRE_AUTH=1` 时，不能只验证“这个用户存在”而不验证“他属于哪个团队”。缺少可信团队解析须拒绝服务，不能退回自报团队。
- 真实团队权限提供方的协议、角色映射与生产接线仍需专门验收。

## 四、生命周期：不要把“删卡”理解成“删正文”

| 用户动作 | 画布侧 | 文档侧 |
|---|---|---|
| 新建并保存文字卡 | 保存卡片和镜像；建立绑定 | 创建或找回对应文档 |
| 编辑卡片正文 | 保存画布编辑后推送文档 | 接收正文更新 |
| 在详情/文档 App 编辑 | 成功同步时更新镜像和预览 | 先保存正文，并返回镜像状态 |
| 改卡片标题 | 改卡片名称 | 不强制改文档名 |
| 改文档名 | 不强制改卡片标题 | 改文档自己的名称 |
| 删除卡片 | 归档绑定 | **保留文档资产** |
| 撤销删卡 | 可恢复因删卡而归档的绑定 | 不自动复活已被显式归档的文档 |
| 归档画布 | 归档绑定，拒绝继续写入；保留只读 | 保留文档，不连带销毁正文 |
| 归档文档 | 解绑；旧镜像可能仍可显示 | 禁止再写或静默重新绑定，保留只读审计 |

画布标题与文档名称不强制联动是数据归属规则，不应再当成“同步漏了一个字段”。

## 五、本轮实际修复

1. **独立文档页面的接口格式不一致**：列表/新建解包、深链定位到真实文档，而不是误把镜像路径当正文。
2. **绑定串文档**：按团队、画布、卡片共同识别；移除仅按卡片 ID 的宿主缓存；每次同步刷新镜像指针。
3. **文件与租户越界**：文档实例文件必须属于目标实例；本地文档 ID 路径穿越/符号链接防护；宿主代理与 legacy 路由不能绕过租户门禁。
4. **删除路径不一致**：UI PATCH 与 operations 共用提交后的绑定协调；删除不再遗留本轮操作产生的活跃绑定；拒绝给不存在的卡片新增绑定。
5. **同步死锁与旧写覆盖新写**：画布提交并释放锁后才调用文档；文档回写文件和卡片在同一画布锁下更新；来源版本随请求传递，旧版本失败前不改镜像。
6. **假成功**：检查 HTTP 失败、超时、镜像冲突；画布 API 返回同步警告并记审计；文档 UI 区分“正文已保存”和“画布已同步”。
7. **详情打开造成覆盖风险**：不再默认把画布副本当较新正文；读取坏响应时不再伪装为空文档。
8. **归档后的隐形写入**：归档文档禁止写入/自动重绑，归档画布拒绝写入。App 页签接入宿主脏状态与离开前保存保护。
9. **测试组件导入失败**：让浏览器文档组件在 Vitest 正确加载，不为裸 Node 导入而破坏浏览器包。
10. **云函数能力宣告不实**：未实现的完整 App actions 不再对外宣称已支持；不把函数构建通过当成完整云 App 上线。

### 检查没有全绿的地方

全仓 `pnpm guard` 与根级 `pnpm typecheck` 仍失败，不能报全仓通过：

- guard：文档组件的 vendor `file:` 依赖规则、MF React 配对规则、未登记的 JS 兼容脚本；本轮期间还有其他会话新增的调试脚本。
- 根级 typecheck：e2e 中已有的 fixture 导入缺失。
- 本轮改动直接涉及的 server/web 包级测试与类型检查通过。这不替代修复上述全仓交付门禁。

## 七、还不能宣称完成的事项

1. **离线/失败重试**：没有持久 outbox；重启后不会自动证明所有历史编辑都已送达。不能盲目重放旧正文，以免覆盖新的文档编辑。
2. **文档并发控制**：文档正文自身尚无 revision CAS，多人同时写仍可能后写覆盖先写。本地多进程共享同一数据根目录也没有跨进程持久锁。
3. **历史数据**：本轮未删除、归档、合并现有用户资产。之前发现的历史残留绑定与重复文档，需要先只读审计、再明确选择保留哪份，不能按数量直接自动清理。
4. **云端**：真实 Appwrite schema、历史丢失的 App scope/teamId、团队权限 provider、生产部署没有验收；没有迁移真实云数据。
5. **范围之外**：并未把 sketch/生图等所有其他 App、Word 导出、图片交付或整个平台管理页面一并宣布闭环。

## 八、如何理解交付状态

本轮交付是：**代码修复 + 回归测试 + 隔离运行验收 + 明确的数据归属规则**。

没有重启或替换现有画布/文档服务，没有迁移真实数据；因此不能承诺你当前已打开的长期运行进程自动使用了全部新后端代码。实际切换仍需由该服务的运行会话统一重建/重启后复验，避免与正在进行的其他调试相互覆盖。

工作区中存在另一会话的并发提交和调试；本会话未执行 git 提交，也未回退它的修改。最终应基于两个仓库的当前完整改动做一次合并审查，而不是只取某个中途提交。
