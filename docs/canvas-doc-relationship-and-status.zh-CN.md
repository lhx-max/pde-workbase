# 画布、文档 App：关系、并发编辑与复制规则

核验日期：2026-10-21。当前报告包含用户明确规则后的第二轮实现；代码、测试、隔离运行与生产部署是不同状态。

## 先看结论

**一个工作台、一个画布能力服务、一个独立文档服务；一份已绑定正文，有两个可编辑入口。**

- 画布工作台是界面，画布 App 是同一画布能力的 API，不是另一份画布产品。
- 文档 App 独立保存正文，编辑器既能单独使用，也能挂到画布里。
- 画布与文档可以同时编辑。不重叠修改尝试合并；同一区域冲突必须保留双方，不允许后写静默覆盖。
- **资产被使用时是复制，不是共享引用**：新文档、新卡片、新可编辑文件。作者的原件、其他使用者的副本互不影响。
- 当前完成的是本地单写服务实例的并发版本保护、持久同步任务及冲突恢复；**不是无条件的零风险协同平台或生产上云验收**。

## 一、谁管什么

```text
画布工作台
├─ 卡片/连线/布局 ──→ 画布 App ──→ 画布存储
└─ 文档详情页签 ──→ 文档编辑器组件 ──→ 文档 App ──→ 文档存储
                                      ↑
                           独立文档页面使用同一编辑器

同一绑定：画布卡片 ⇄ 带版本、基线和状态的同步 ⇄ 文档正文
资产使用：来源资产 → 复制不可变版本字节 → 新卡片/新文档身份
```

已绑定正文的权威存储在文档 App。画布 `node.text` 与文件是渲染/操作镜像；画布编辑会先保存本地草稿，再提交正文变更。没有安装文档 App 时，画布仍可独立保存，但不能声称文档已经保存。

**“正文已保存”和“画布已同步”始终是两个结果。** HTTP 200 不能替代镜像确认。

## 二、同时编辑怎样避免丢内容

### 文档入口

读取得到 `{content, revision, meta}`；revision 是正文 UTF-8 的 SHA-256。保存携带 `baseContent` 与 `expectedRevision`。

- 当前正文等于基线：正常保存。
- 当前正文已经等于提交内容：幂等确认。
- 对方修改了别的位置：在同一文档写锁内三方合并。
- 同一区域冲突、缺乏可靠基线或超出安全合并上限：409，返回当前正文、版本和本地草稿；不猜哪份新。
- 修改既有正文却不带版本/基线：428，不允许盲写。原始文本接口可用 `If-Match`。

合并是有界的纯文本 diff，不是逐字符 CRDT/OT 协作、光标共享或所有富文本结构的语义合并。无法证明安全时，宁可明确冲突。

### 画布入口

画布事务提交前先落盘同步 intent，提交后释放画布锁再调用 App。发送前再次确认该卡片、内容及提交版本仍存在，未提交或已被替代的草稿不能外发。

画布与文档使用不同版本：画布是递增 number，文档是正文 hash，不能混用。文档回写同时携带观测画布版本、正文基线、目标 nodeId/docId 和文档 revision。即使 GET 到一个新的画布版本，也不能覆盖基线之外的本地修改。

### 编辑器与冲突界面

- 两个文档编辑入口使用同一版本化组件；定时/焦点刷新发现远端变更。
- 干净编辑器跟随远端；脏草稿不被轮询、迟到读取或较早保存的合并结果替换。
- 保存期间继续输入，如果无法安全采用合并结果，则暂停自动保存、保留草稿并显示远端版本。
- 画布显示待同步/冲突状态；“采用画布稿”和“采用文档版本”都要求明确确认，并再次校验双方观测版本。409 后刷新，不重放旧选择。
- 打开详情是只读操作。`preferContent` 只是调用时卡片快照，不是覆盖权限。既有镜像零写入；缺文件也只按已保存节点与画布版本补建，不拿缓存草稿盲写。
- Doc镜像确认不能包装成新的本地文字事件回写。确需发布的本地事件带projectId且一次消费，setter变化不能重放旧稿；远端镜像以服务器状态订阅为准。
- 旧通用文件查看器不是第三个协同正文协议。无版本的JSON/base64/multipart覆盖活动Doc镜像会返回428，防止绕过保护；该查看器现有草稿不因此标为已保存，请改用卡片/Doc页签或版本化App files。普通新文件、未绑定文件及create-only上传仍可使用。

## 三、断网与重启

### 画布侧

[同步日志](<../apps/server/src/storage/document-sync-journal.ts>)逐卡片保存 intent、基线、调用者、代际、结果与冲突正文；独立文件、严格 schema/hash 身份校验、原子写和 fsync。

- 离线连续 A→B→C 合并为最新待投递 C，并保留尚未确认的共同基线 A。
- 重启重新读取任务；提交未确认、卡片删除、画布归档、租户改变时不重放。
- 旧 callback 和旧确认不能覆盖较新的 intent。若绑定变成另一docId，先持久清除旧文档的共同基线；重试也不能拿旧身份的基线合并另一文档。未知新基线只允许内容已相同的安全确认，否则保留双方等待解决。
- 临时失败退避重试；权限、归档和冲突不冒充成功。重试仍检查当前授权。

### 文档侧

文档服务有显式数据根下的持久镜像队列，保留正文版本、最后确认的画布基线与 actor；不持久化 token/cookie。离线合并、进程重启和绑定部分失败均有恢复路径。

**仍有跨存储事务边界**：正文提交和镜像队列落盘不是一笔分布式事务。若恰好在两者之间崩溃，重启会对已有日志与当前正文进行对账，不能继续显示旧的 synced；有可靠基线时由当前授权用户确认恢复，不能冒用旧编辑者。首次尚无日志/共同基线时不能猜测覆盖，需画布幂等重投或显式重新对账。

因此“持久队列已实现”不等于承诺任意崩溃点下 exactly-once 或全自动无冲突恢复。

## 四、复制与生命周期

| 动作 | 结果 |
|---|---|
| 保存文字卡 | 新卡按团队＋画布＋nodeId 创建/找回自己的文档 |
| 从资产使用正文 | 先验证来源访问权，再复制到新文件/新卡片/新文档；不继承原绑定或 owner |
| UI/API 复制卡片 | 新 nodeId；立即分离共享镜像路径，不等第一次修改才分离 |
| `doc.copy` | 新 docId，当前团队/调用者归属，无原 nodeId/mirror/归档状态 |
| 删除卡片 | 只归档绑定，正文保留 |
| 撤销删卡 | 可恢复 card_removed 绑定，但不能挤掉新绑定或复活显式归档资产 |
| 归档文档 | 禁止写入，保留可读正文；按 nodeId＋appId＋appInstanceId 条件解绑 |
| `doc.restore` | 显式恢复正文编辑，清除旧绑定；不会抢回原卡片 |
| 归档画布 | 拒绝继续写入，保留画布与文档数据 |

卡片标题与文档名称可以独立变化。每个卡片/编辑 App 最多一个 active 目标；坏绑定文件、重复活跃记录必须 fail closed，不能静默当空库覆盖。历史残留数据本轮不自动迁移。

默认 `local-personal` 是单用户本地资产库，不是跨团队共享服务器。它仅允许 local/local；API、服务和图片引用旁路都有保护。真正跨团队使用需由已授权的外部资产来源提供，**复制不授予源资产读取权限**。详见 [复制与授权边界](<asset-library-copy-boundary.zh-CN.md>)。

## 五、App 接入与租户

- 宿主只发布正文变化意图；文档专用 API 留在薄适配器内。未为了一个 App 建设通用大框架，也不声称所有新 App 都能零改宿主接入。
- 独立 App 的编辑器以仓内版本化 vendor tarball 接入，不链接另一个开发目录。guard 只允许仓内真实 vendor tarball，目录链接与越界 `file:` 仍禁止。
- `platform` 表示能力可用范围，不表示正文公开共享；资产仍按团队隔离。
- 调用者身份贯穿请求、队列和审计，不一直套用资产创建者。同步状态/重试/解决不能泄露被拒App的缓存远端正文；权限规则损坏或IO读取失败显式报错，不能降级为默认允许。
- 文档开启 `DOC_REQUIRE_AUTH=1` 必须同时具备已验证用户与可信团队 provider；没有可信团队信息就拒绝，不退回自报团队。
- Appwrite 不提供本实现所需的跨实例条件写。已有正文变更默认拒绝；必须显式 `DOC_APPWRITE_SINGLE_WRITER=true` 才进入约定单写者模式，这不是分布式 CAS。

## 六、实际验证与交付

本轮真实双进程 [HTTP 验收工具](<../e2e/canvas-doc-runtime.ts>)通过8组：出生绑定、双入口独立修改合并、重叠冲突与版本化解决、文档离线队列重启、画布离线队列重启、UI式复制卡片隔离、独立文档复制及跨团队拒绝、归档恢复与迟到条件解绑。

测试发现并修复过真实跨服务循环等待：绑定校验不能请求正在持有镜像队列的 doc state，而要走不依赖该队列的正文读取。纯 mock 通过不替代这类实际验收。

包级测试、构建、浏览器最终证据与计数以 [运行验证记录](<runtime-verification.md>)最新批次为准。以前的 [独立文档持久化截图](<verification/doc-ui-persisted-2026-10-21.png>)是前一轮证据，不冒充本轮全部内嵌交互通过。

### 仍未完成/不在承诺内

1. 多个 doc 服务进程或多个 canvas 服务进程同时写同一数据根的分布式并发控制；目前支持每个存储根单写服务实例、多编辑客户端。
2. 字符级实时协作、光标共享、所有大型/结构化正文的自动语义合并；冲突时明确保留双方。
3. 正文与跨 App 投递原子提交；前述崩溃间隙需要对账/确认，不假装全自动。
4. 真实团队 provider、SSO、Appwrite schema/权限、正式部署与云端故障恢复。Appwrite 归档恢复后旧确定性绑定 ID 再次创建会安全拒绝，尚未引入云端绑定 generation 迁移。
5. 历史重复/残留绑定清理、全部生命周期管理页面、整个画布复制、所有其他 App 与图片/Word 导出的整体验收。
6. 根级 release gate 仍有其他组件 React 配对、未登记脚本和 e2e 缺失 fixture 问题；不能宣布全仓全绿。

本轮不修改用户现有正文、不清理历史资产、不重启现有画布/文档服务，也未执行 git 提交。实际使用前需由负责长期服务的会话统一切换两个后端与编辑器版本后复验；不能只升级其中一端再让旧客户端盲写。另一会话有并行改动，未回退它的代码。
