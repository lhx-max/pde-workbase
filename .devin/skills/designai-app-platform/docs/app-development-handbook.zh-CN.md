# DesignAI App 架构与开发白皮书

文档版本：3.3.1。修订日期：2026-10-23。适用读者：新加入的开发者、评审者、接手维护者和 AI Agent。

本白皮书定义在 DesignAI 架构中开发、交付和接入 App 的共同要求。它既说明架构与责任，也给出从需求到运行验收的工作路径。具体字段由专项合同规定；业务字段由 App 合同定义。阅读本文件不表示已经获得仓库、平台或数据权限。

**用语约定**：“必须/不得”为适用范围内的交付要求；“应”为默认实践，偏离时在合同中说明原因；“可”为按业务选择。标注“历史/示例”的内容不构成当前服务能力或发布状态。

## 文档体系与使用方法

| 层级 | 内容与维护责任 |
| --- | --- |
| Skill 入口 | 任务识别、阅读顺序与关键约束，不保存完整接口样例或实时进度 |
| 本白皮书 | 产品边界、架构、责任、完整开发流程与验收框架 |
| 专项合同 | API profile、卡包、互联、正文同步、身份/持久化与制品的精确约定 |
| 每 App 的 APP_CONTRACT | 本 App 的业务字段、资源、负责人、适用合同、部署方式和验收范围 |

| 执行证据与问题案例 | 实际版本、命令、输出、故障和修复；不直接替代规范正文 |

开发前先查 [资源目录](platform-resource-catalog.zh-CN.md)，再填写 [APP_CONTRACT](../templates/APP_CONTRACT.template.md)。首次开发按本文§10执行；已有 App 接入时逐项核对差异，不重新复制业务后端。

## 规则适用范围

| 层级 | 适用内容 | 不得扩大为 |
| --- | --- | --- |
| 所有业务 App | 可信身份、数据归属、公开 API、版本/回执、云端持久化及真实验收 | 每个 App 都实现全部画布路由或自建组织权限体系 |
| 画布关联 | 卡包、布局、绑定、镜像、资源引用与同实例打开 | 所有 App 必须先建卡才能使用 |
| 外部 DA/MA 接入 | 目标宿主的组件、manifest、Provider、正式登记、实例与动作授权 | Canvas COI 自注册等于 MA 应用发布 |
| 工具与示例 | PDE 初始化/部署、历史配置和特定实现的并发前提 | 强制改造现有技术栈、扩大 ACL 或自动升级依赖 |

共享责任由本白皮书定义；专属协议仅在 APP_CONTRACT 选择对应能力/profile 后适用。目标仓规则和宿主已发布合同决定实际技术栈与外部接口，案例和历史状态不得覆盖现行合同。

## 接入范围与阶段选择

一个完整交付周期包括独立业务闭环、云端持久化、可安装制品、目标宿主集成、Agent 调用与目标环境验收。每次任务在合同中明确交付到哪一阶段；未纳入的阶段写明原因，已纳入但依赖不足的阶段记录具体缺口，不标通过。

计划接入 DA/MA 的独立 App 必须在编码前核对 [Kit 接入合同](da-plugin-kit-integration.zh-CN.md)：surface/包装层、实例映射、动作及版本、网络与认证接缝。正式登记可以晚于独立业务开发，合同准备不能延后到所有代码完成之后。纯 JSON 卡包不因此承担独立 App 后端。

实现与验收状态由版本化执行报告维护，不写入通用架构结论。新增 App 必须使用自己的实例、制品和目标环境提供证据。

## 1. 架构概念与交付物

### 云端默认与本地测试边界

本架构以 Appwrite 云端保存权威业务状态和资源。本地模式只用于显式隔离测试；不得把历史本地实现作为正常运行的默认回退。

- 正常开发/联调的画布状态、文档和资源使用各自 Appwrite 存储；需持久化的恢复/同步信息也须明确云端方案。不能用整目录搬云替代业务归属和协议设计。
- 缺少云端配置、授权或实际 schema 时明确不可用；不能自动创建另一套本地业务资产并把成功响应当作云端完成。
- 显式隔离的测试可使用本地 fixture；后端可使用可丢弃临时目录/缓存。不得依赖某台电脑的历史目录恢复业务。
- 项目菜单、业务空间、身份/组织及宿主应用实例目录由基座负责。我们保存自己的业务状态、归属与必要映射，不重复建设宿主项目名单或组织真源。
- 验收至少验证真实云端写入、读回、空工作目录重启后的恢复，以及适用的权限拒绝；本地测试、包安装或已部署函数都不能单独替代。
- 既有本地存储实现及云端恢复/鉴权缺口须逐项验证和改造；规范条款本身不构成实现完成的证据。

### 1.1 产品与交付物

| 名称 | 是什么 | 不应混同的对象 |
| --- | --- | --- |
| App | 有业务能力、权威数据与公开 API，能通过独立壳运行，也能嵌入宿主的小产品 | 一个 React 组件、一个卡种或一个 npm 包 |
| App 后端 | 校验权限、版本、输入，执行业务、持久化、返回结果的服务 | npm UI 包；宿主数据库 |
| surface | App 可嵌入的 React 界面，使用公开 props/API 适配器 | 独立 Web 站点；自带另一套服务端 |
| 独立壳 | 挂载同一 surface 的 `apps/web`，供独立使用和自闭环验收 | 另一套编辑器实现 |
| 卡片 | 画布中的一个实例；有卡片 ID、kind、位置、尺寸、标题与业务内容/引用 | 一整个 App；每张卡一个 npm 包 |
| 卡包 | 提供一种或多种卡片渲染器及可选服务端动作的 npm 包 | 每个卡包都要自建后端/数据库 |
| 宿主 | 安装组件、管理页面/标签与上下文的应用 | 数据库；Agent 执行环境 |
| App 包装层 | 把某个宿主的 context、文件、会话等合同转成 surface 需要的 props/API | 修改宿主 SDK 或复制编辑器业务 |
| CLI | Agent/人使用的命令行 HTTP 客户端，调用同一个权威后端 | 第二份数据存储；安装后自动被 MA 发现的工具 |
| Skill | 解释能力发现、参数、调用顺序及错误恢复的说明 | 认证凭据；可执行权限；工具安装本身 |
| manifest | 某个协议中的能力/安装声明 | 可执行实现；权限凭据；运行验证报告 |
| Provider | 外部 MA open-platform 信封到 App 业务服务的适配入口 | 身份提供方；只要 actor 有值就可信的公开 API |

“宿主”有两层：**画布工作台可以宿主文档编辑器；MA-V 又可以宿主整个画布 App 和文档 App**。同一个 App 可以有多个宿主适配器，不为每个宿主复制业务后端。

### 1.2 三条实际连接

```text
渲染/安装：业务卡包 → 画布组件 → MA-V 的画布 App 包装层 → MA-V 标签
                        文档组件 → 文档 App 包装层 → MA-V 标签/画布详情

人操作：surface → 注入的 API/transport → App 后端 → App 权威存储

Agent 操作：MA 执行环境 → 已安装 CLI 或已注册工具 → 认证网关/Provider
                                                → 同一个 App 后端/存储
```

npm 交付代码，不替代应用登记，也不部署数据库。卡包安装到画布；surface/包装层安装到宿主；CLI 安装到 Agent 的执行环境；后端独立部署。宿主安装 UI 包时，不要求复制部署一份 App 后端。

### 1.3 该做哪一种

| 需求 | 最小开发面 |
| --- | --- |
| 新增一种展示/轻编辑卡，内容只是可序列化 JSON | 卡包，使用 `data` 和 `onPatch`，文件走 `ctx.files` |
| 卡片有复杂编辑器、资产生命周期或独立使用价值 | 独立 App；卡面/入口可另提供卡包 |
| 已有 App 要接入 MA-V | surface + MA-V 包装层 + MA manifest + Provider，复用业务服务 |
| 已有 App 要给 Agent 用 | 公开动作与 schema + CLI/工具接缝 + Skill，复用业务服务 |
| 移动卡、改尺寸、连线、排列 | 画布动作，不给每个 App 再造一套布局 API |

不是所有 App 都必须绑定卡片：独立创建的文档可以没有画布；从卡片打开的详情必须找到**原绑定实例**，不得隐式创建另一份文档。宿主某入口是否同时建卡，是该入口的产品规则，不是全局一一对应规则。

## 2. 开发合同与范围定义

在新 App 仓复制 [APP_CONTRACT 模板](../templates/APP_CONTRACT.template.md) 为 `docs/APP_CONTRACT.md`。先填实际业务目标、动作、数据归属、宿主 profile 和验收出口，再写代码。`待提供` 是有效状态，但不得伪造外部接口补空。

| 必填信息 | 需要做出的决定 |
| --- | --- |
| 身份 | appId/slug、包名、kind、actionId、moduleId/exportName 各自是什么 |
| 功能 | 最小独立任务、编辑卡入口、Agent 任务各一个 |
| 权威数据 | 每种实体由谁保存；谁仅保存引用/镜像；复制和归档的含义 |
| 接缝 | 组件 props、业务 API、COI、MA Provider、CLI 分别支持什么 |
| 运行 | 本地/staging 的地址、认证来源、存储模式、单写者限制 |
| 失败 | 冲突、断网、不确定写入、权限失败、取消/重试如何处理 |
| 验收 | 复现命令、测试数据根、UI 路径、回执、重开及失败证据 |

开发者可以独立决定内部模块组织；影响外部协议、权威数据或宿主接口的决定要写入合同。外部缺项写成“接口/字段/提供者/阻塞哪道验收门”，明确所缺字段、提供方和验证方式。

## 3. 责任、标识与数据权威

### 3.1 谁负责什么

| 责任方 | 拥有 | 不能靠它证明 |
| --- | --- | --- |
| 外部基座 | 身份/组织、应用发布与实例、会话关联、宿主标签、MA 调度 | 我们的正文已保存、App 内部版本正确 |
| 画布 App | 卡片/连线/布局/画布版本、可发现的卡种、卡↔App 关联接口 | 文档正文镜像一定已送达 |
| 业务 App | 业务正文/资源、资产元数据、条件写、冲突与生命周期 | 身份来自自报 header 就已认证 |
| 卡包 | `data` 格式、卡面渲染、自定义动作语义 | 自行更改画布信封、另开本地存储绕过持久化 |
| surface/包装层 | 编辑草稿、状态显示、API 适配、宿主生命周期对接 | 客户端校验可以替代后端授权 |
| CLI/Skill | 能力发现、请求编排、错误报告、读回确认 | Agent 环境已安装、已授权、已能访问服务 |

应用方适配对方已发布合同；不修改外部宿主、共享 SDK、菜单或 MA 调度来证明接入成功。宿主确有缺口时，提供最小复现和所需能力，由其维护者处理。

### 3.2 ID 不能互换

| 字段 | 语义 |
| --- | --- |
| `appId` / MA `manifest.slug` | 人可识别的能力标识，例如 `doc`；两者的对应关系由适配器声明 |
| npm 包名 | 代码分发名称；不从 appId 自动推导 scope 权限 |
| `kind` | 卡种，例如 `card.acme.brief`；不是实例 ID |
| `nodeId` | 某张画布内的卡片 ID；绑定必须连同画布和团队校验 |
| Canvas 内部 `projectId` / COI `instanceId` | 当前实现的画布数据身份；不是外部项目 `bizId` |
| MA `bizId` / `sessionId` | 外部业务空间/会话，由基座提供 |
| MA `applicationId` / `applicationInstanceId` | 正式登记的应用/实例身份，当前分别匹配 `app_...` / `ai_...` |
| `providerInstanceId` | 外部实例在 Provider 的解析键，可能是别名，不保证等于 docId 或画布 ID |
| `docId` / 其他 App 实例 ID | 业务 App 保存正文/业务状态的身份 |
| `projectFilePath` / `mirrorPath` | 受实例作用域约束的相对路径；不是全局资产主键或授权凭证 |
| `operationId` / `idempotencyKey` | 一次逻辑写入的稳定身份，不是业务实例身份 |

示例：当前画布 Provider 用 `tenantId + applicationId + providerInstanceId` 解析内部画布，不能把外部 `bizId` 直接当画布 ID。文档 Provider 可以用 `ma:<pid>` 别名找到正文。实现参见 [画布 Provider](../../../../apps/server/src/routes/canvas-provider.ts)。

### 3.3 权威存储与文件

- 画布信封和布局由画布服务保存；纯卡片业务 JSON 可以由画布状态承载，卡包无需独立数据库。
- 有权威业务 App 的正文由该 App 保存。画布里的文字、预览、文件可以是可编辑镜像，不是第二个盲覆盖源。文档双入口遵循 [正文增补合同](document-sync-contract.zh-CN.md)。
- App 使用其权威服务的 Appwrite 存储；本地模式仅供显式隔离测试，不能作为正常开发/联调回退。独立性指责任隔离，不要求每个 App 自建数据库引擎或另起进程。不同服务不直查/写对方私有库。
- App 自有资源走 App 文件 API；画布工程镜像走画布文件通道；卡包文件用平台注入的 `ctx.files`。**不得把“共享文件通道”理解为给 App/浏览器发另一服务的桶凭据。**
- 资产使用的既定产品语义是复制：授权读取源版本后创建新的可编辑身份、文件与归属。只有显式选定“打开既有绑定”才编辑同一实例。
- 删除/归档如何保留正文、解除绑定、恢复要写清楚。不能让迟到的旧解绑通知删除新的 active binding。

生图 App 的业务权威必须位于独立生图后端及其私有云资源中。配置、任务、动作回执、原图/结果图、编辑工程和恢复状态不得继续默认保存为画布业务状态。画布仅保存布局、资源引用、预览与必要的绑定/投递映射；跨 App 通过公开 API 和受授权的资源引用互通。历史画布承载 profile 与独立后端分别验收，不能仅更换桶名就宣称领域边界已经完成迁移。

云端资源实际标识、归属与审批见 [资源目录](platform-resource-catalog.zh-CN.md)，数据关系见 [数据模型](data-model.zh-CN.md)；本地绑定索引、回执、同步队列与云表不是同一件事。不能因“不新建云绑定表”删除已用的协议/本地恢复机制，也不能凭有一个 `.ts` 文件宣称云表已初始化。

### 3.4 后端必须形成的闭环

| 能力 | 开发与验收要求 |
| --- | --- |
| 输入与资源边界 | 严格校验 body、路径与动作参数；显式 null、数组、未知字段或非法路径应得到明确错误，不触发500或副作用 |
| 身份与授权 | 区分认证、动作授权和资源归属；按适用的 team/biz/MA实例检查；缺字段不作通配，旧数据不自动认领 |
| 数据与 schema | 交付空环境预置/迁移说明；字段、必填性、长度、索引、私有ACL和异步创建状态与代码一致 |
| 写入一致性 | 版本检查到提交受同一并发保护；单写者部署有实际独占锁；正文、重命名、归档、绑定和后台投递均遵守 |
| 持久确认 | 成功响应在规范字节、索引和必要恢复记录确认后返回；部分成功/flush失败明确报告，不返回仅内存成功 |
| 回执与幂等 | 同键同请求重放，同键异参冲突；含完整调用作用域；有键声明不能因缓存淘汰导致重复执行；无键临时回执有边界 |
| 文件与导出 | 读写、Range/下载、导出结果及后台取源均校验资源授权；路径与符号链接不能逃逸；不把桶凭据发给浏览器 |
| 恢复与运行 | 空缓存重启读回、锁竞争、失败后恢复、备份与回滚有实际证据；日志中的监听地址与真实进程一致 |

读写授权按动作语义判断，不能将所有 POST 视作写入，也不能将所有 GET 视作可公开读取。仅对已定义的精确路由/动作授予权限。

需要单写者前提的所有变更共用该前提，不得只在正文保存接口检查。停机按停止接收新业务、排空已接受操作、刷写持久状态、释放自身锁的顺序执行；客户端断开不代表业务操作结束，空闲预连接也不能无限阻止退出。验收完整页面操作后持续轮询时的关停、最终退出码与锁状态；未确认旧写者退出，不抢占崩溃锁。

回执和恢复账本须验证单条大结果及长期累计数据均适配实际存储上限，不将所有历史键无限追加到一个有固定大小限制的槽。分片内容确认后才能发布索引；持久格式升级保留旧回执，声明崩溃恢复与旧版本回滚边界，详见[可靠性合同](unified-app-delivery.zh-CN.md)。

### 3.5 异步处理与有成本操作

异步动作必须定义任务身份、可观察状态、结果与失败、取消、重试、服务重启恢复及回填条件。提交前持久化原请求及目标的实例/资产/节点/版本；目标被修改、删除、撤权或任务已取消后，迟到结果不得覆盖当前内容。

展示用 URL、受认证资源桥 URL、规范逻辑路径和后端交付描述是不同对象。后端接收稳定的规范标识，浏览器地址由资源桥解析；规范请求在进入持久 outbox 前确定，恢复不得改写旧请求的幂等摘要。

可配置模型、授权 ready、实际执行成功和产物质量分别验收。取消本地调度、供应商确认取消、停止计费/退费分别报告。受控执行器的取消测试不证明真实供应商退款；不得为重试自动生成新的有成本任务。

已声明为原子批次的业务提交必须完整可见或维持原状，原子边界须在合同中写明。跨 App、对象存储、队列与供应商执行不假设存在分布式事务；采用持久阶段、条件发布和恢复对账，分别报告已受理、业务已保存、产物已落库与镜像/回填送达。不得以整体原子性的文字承诺掩盖这些阶段的部分成功。批量或多步骤任务先持久保存已完成产物及其回执，后续失败不得丢弃已付费产物，也不得靠重新执行有成本任务补齐。同一逻辑操作使用精确幂等键加基线版本；结果不确定时先查既有回执，不得换键重复提交。

## 4. 代码分层与接口边界

```text
designai-app-<id>/
  apps/server/src/       领域服务、路由、认证/Provider 适配、存储入口
  apps/server/tests/     业务/协议/存储测试
  apps/web/              独立壳，挂载同一编辑器
  packages/<id>-surface/ src/、tests/、构建与包出口
  packages/contracts/   可选：需要跨包共享的纯 DTO/schema
  packages/<id>-cli/     采用 CLI 交付时使用；实际包名按发布清单确定
  docs/APP_CONTRACT.md   本 App 实际接入合同
  docs/verification/    可复现记录与已知限制
```

这是职责模板，不是要求复制空目录。现有仓库按已存在边界实施，不为符合目录图重构。新代码 TypeScript；画布仓使用 Node 24、pnpm 10.33.2，画布组件约束 React 18；其他 App 在合同登记其维护者确认的工具链，实际宿主 renderer、peer 与 SDK 另做兼容验证。服务端不得导入 surface 私有实现，浏览器不得导入存储/凭据模块。

独立启动和嵌入使用同一业务 API 与组件。不要为了嵌入成功改成直接读宿主文件，也不要在包装层再维护一份正文。数据根由入口显式解析并注入；禁止依赖另一个 checkout、cwd、开发者绝对路径或本机 symlink。

doc 参考仓为 [公司 Git `design/designai-app-doc`](https://git.corp.kuaishou.com/design/designai-app-doc)，私有仓、默认main，需相应Git读取权限。可以读它的公开接口/测试、按其许可证和来源要求适配代码；不能把作者本机目录写进新 App 的 package.json。参考仓不可用时按本手册与合同实现最小领域服务，不猜其私有 API；若某宿主类型/schema不可得，则相应接入门标待提供，独立业务继续做。

### 4.1 surface 的最低合同

- 声明 props、必需 API 方法、可选能力以及未配置行为；`read/write` 与版本化 API 的能力差异明确。
- 导出实际 TS 类型和 CSS，组件不自行登录或内置服务端密钥。
- 文档独立壳与卡片详情使用同一编辑器与同一版本化读写适配器；画布 surface 另有公开 `transport` 和 `uiHost`，见 [包说明](../../../../packages/canvas-surface/README.md)。
- 只有经认证的配置决定 API/资源地址；不能从任意 URL 查询参数读取带凭据的服务地址。下载、图片、Range、上传、SSE 要分别核可达性与授权。
- dirty 草稿不能被轮询、旧读取或迟到保存覆盖。状态至少区分 loading、saving、saved、offline/error、conflict；需要镜像时另显示同步状态。
- 实例切换先保存/flush；失败保留草稿并阻止受控切换。只使用宿主已提供的生命周期；没有相应接缝要记录限制，不能承诺强关/断电不丢尚未提交的输入。
- 当前画布有模块级 host bridge，同一 JS realm 多活动实例未认证；默认一次挂一个，A/B flush/unmount/switch 单独测试。
- 共用宿主的一份 React renderer；不打包另一份 React 消除 peer 冲突。当前画布包锁 React/ReactDOM 18.3.1、xyflow 12.8.5；将来兼容矩阵由实际包版本与目标宿主测试决定。
- 卡面复用画布现有壳和CSS变量，不重画平台UI；独立编辑器由App负责，但应说明最小宽高、滚动、焦点/快捷键、弹层挂载与样式作用域，不能让全局CSS污染宿主。原生浏览器、媒体/模型、导出、文件选择等能力用已提供适配器；未接入就显式不可用，不在surface私自恢复原桌面平台。

### 4.2 后端与存储的最低合同

- 输入、文件路径、实例、action、响应按 schema 校验；路径穿越、符号链接和跨实例引用不可放松。
- 读和写都检查真实身份、团队、目标实例、动作权限；查不到授权 provider 时 fail closed。
- create 先定幂等绑定；read 返回真实状态/版本；write 校验版本与基线；archive/copy/restore 作用域明确。
- UI/API/Provider/CLI 使用同一领域服务和持久化实现。动作逻辑不复制到每个传输入口。
- 存储后端明确 local、Appwrite、持久操作日志/队列。部署必须声明可承受的单写服务进程数、恢复与备份；进程内锁不是分布式 CAS。
- 异步生成需声明任务 ID、queued/running/succeeded/failed/cancelled、回执/结果、取消与幂等。没有任务能力时先交付同步最小功能，不声明虚构事件/进度。

## 5. 接口 profile、版本与请求语义

| 接口 | 调用者/作用 | 合同来源 |
| --- | --- | --- |
| App 自有 API | 独立壳、surface 适配器；业务领域接口 | App 公开 schema/DTO 与实际路由 |
| Canvas COI / P1–P24 | 我们的画布平台目录、动作、文件、绑定、CLI | [App 规范 §4.2](app-development-spec.zh-CN.md#42-统一协议合同v1唯一标准) |
| MA open-platform | 外部基座通过 Protocol `1.0` 调 App Provider | App规范§4.5–§4.6 + [示范/基座逐项对照](da-plugin-kit-integration.zh-CN.md#2-合同逐项对照)；区分调用者→MA与MA→Provider |

**P1–P24 是角色分工，不是每个 App 实现 24 个服务端路由。** 目录/注册/代理/治理由我们拥有的画布宿主实现；业务 App 提供自己的 manifest、实例/动作及适用文件接口；卡包通常不写 HTTP。不适用的能力说明 N/A 原因，不伪造成功路由。

COI manifest及 `{requestId,data}` 响应包不用于替代MA manifest/Provider结果；Provider快照用content，动作结果用data。COI manifest 用 `actionId/mode/async` 等字段；MA manifest 用 `id/effect/inputSchema/requiredPermissions` 等字段，不能直接互换。相同的业务词表通过显式适配映射；新增参数要同步 schema、版本和实例迁移计划。

注册到我们画布目录的 `endpoint` 是**协议根**，例如 doc 的 `https://<service>/api/apps/doc`；MA 的 `provider.baseUrl` 则是按网关约定拼 open-platform 路径的根。这两个地址不能共用一条未经转换的配置。宿主 `fileClient` 管的会话文件与 App 自有资产/正文、画布工程镜像也不是天然同一份存储；若业务要互换文件，明确授权、导入/复制及文件ID映射，不直接把路径或文件ID混用。

### 5.1 写入、幂等与回读

执行顺序：**发现能力 → 定位获授权实例 → 读状态和版本 → 校验输入 → 提交 → 回执/状态读回 → 同实例 UI 确认**。

- 画布 COI 批处理：`POST .../instances/:id/operations`，顶层 `{operationId, baseRevision, operations}`。
- COI 单动作：`POST .../instances/:id/actions/:actionId`，`{input,expectedRevision}`，幂等键在约定 header。不得把批处理信封随便塞给一个单动作。
- MA Provider：顶层 `expectedRevision` 是 Provider 正整数版本；画布当前投影为 `coreRevision + 1`，不直接当 COI `baseRevision`。
- doc 正文版本当前为 SHA-256 字符串，正文基线/版本在业务 `input` 中；Provider 外层整数版本是另一层检查，不能自动代替正文基线。严禁“先读取最新基线再盲覆盖过时用户稿”。
- App 合同可明确允许“规范内容字节相同”的无变更收敛：即使业务内容基线已过期，也不推进内容版本、Provider 版本或更新时间。该规则不是同键回放，不适用于不同内容覆盖或有副作用任务；测试必须分别验证相同内容无变更与过期不同内容冲突，不能仅以 HTTP 200 判定写入发生。
- 不确定写入保留原逻辑操作 ID 和请求体，先查回执；重试、409 解决和业务重复创建是不同动作。回执范围（内存/持久、保存期限）必须公开。
- 400 参数错；401/403 身份/权限错；404 实例或动作不存在；409 冲突；428 缺前提；501 未实现；503 未配置/不可用。实际错误码按所属 API，不把所有失败都变成 200。
- 正文保存成功与镜像同步成功分别确认。网络超时不能显示“已保存”，模型回复“完成”不算回执。

CLI 的服务端点、应用 ID 和实例作用域按目标 App 明确选择。使用同一通用 CLI 不代表其他 App 的路由位于画布服务；先发现该端点公开的 manifest，再使用对应应用能力。

当前 CLI 的 `apps call --body-file` 把文件作为 `input` 封装；源码另已提供 `--expected-revision` 与 `--idempotency-key`，回执使用 `apps receipt`。实际安装的CLI版本仍须核对 `--help` 和对应包，不能把当前源码能力反推给旧包。其他完整信封用其已有 `request` 通道；这不是自动获得MA执行环境授权。

## 6. 卡片与业务 App 互联

分两件事验收：卡面挂载；卡片与 App 资产互联。卡包脚手架见 [卡包合同附录A](canvas-card-pack.zh-CN.md)，不是另起一套渲染框架。

1. 卡包按 [卡包合同](canvas-card-pack.zh-CN.md) 提供 `card.<team>.<name>`、`dataVersion`、渲染器及可选动作。核心 kind 覆盖按平台已有覆盖合同处理，不能借新卡包未经授权抢占保留前缀。
2. 前端把卡包登记进 `packages/canvas-workbench/src/packs.ts`；服务端 `./server` 纯服务入口登记进 `apps/server/src/card-packs.ts`。服务端也要登记卡种，无 handler 也不能省略，否则创建会被拒绝。
3. 卡壳/布局归画布，内容渲染/轻编辑归卡包；数据更新走 `onPatch`/公开动作，文件走注入文件端口。服务端不能导入 React 卡面。
4. 有深编辑 App 时声明 `editorApp`/`editorKinds` 对应关系；明确 card→业务实例映射、权限与打开参数。目录里有 App 不代表卡种 renderer 已安装，反过来也一样。
5. 新卡首次提交正文按业务约定建立资产；再次编辑找回同一绑定。打开既有详情默认读，不因镜像与权威正文不同自动回写覆盖。
6. 验证“卡内编辑→App读回”“App编辑→卡片更新”“复制后独立”“归档/恢复”“A/B 切换”；纯卡包 N/A 的部分写清理由。

归档/恢复必须区分稳定的业务身份、MA Provider 定位与画布卡片/镜像关联。恢复时可按合同解除旧画布关联，但不能顺带删除仍应生效的 Provider 定位；副本不得抢占源实例的定位。归档后的原键回放、显式恢复、恢复后的同 Provider 读取，以及正常重启后的重复恢复，都须单独验收；不能只查业务行仍在就宣布恢复闭环。恢复已处于活动状态的实例时，遵守声明的无变更语义，不额外推进版本或清除关联。

现有核心卡不能假设一个 `node.update` 适用全部类型。图片用图片动作；草图、视频、分镜各有领域动作。查询 live `cardCapabilities`，以 [能力矩阵](canvas-card-capability-matrix.zh-CN.md) 的验证范围为参考。

接入工具仓为 [design/design-agent-plugin-kit](https://git.corp.kuaishou.com/design/design-agent-plugin-kit)，默认分支 `master`。仓库地图、SDK/registry/Preview职责、新App准备清单及文档App实测边界统一见 [DA / MA Plugin Kit](da-plugin-kit-integration.zh-CN.md)；先核对目标发布版本，将已提交合同与未提交的实验适配分别记录。该仓展示基于目标后端的 App 接入形状；Preview 用于辅助验证，不代替后端。逐项对照包含合同来源和不可照搬的示例默认值。

### 7.1 兼容基线与实际 props

2026-10-23 核对基线为 `design-ai-client/yihan-dev-ma@367127668da7e35daf0fa7393040e920a339d069`（早期记录为 `fa9475183`）、Plugin SDK 1.0.0；这是可更新的兼容记录，不是不可变公司标准。目标 schema 位于该仓 `packages/contracts/src/api/ma-applications.ts`。

编辑作用域必须包含应用版本及适用的租户、用户、应用、实例、Provider、业务与会话字段；共享状态可按专项合同排除非身份字段。按字段值判断变化，不能仅以 context 对象引用作缓存依据。宿主复用并原地修改对象时也必须重验；凭据工厂使用不可变快照，旧作用域的回调/资源通道不得对新编辑器生效。同值同版本的重渲染保留草稿与未确认请求；不得把旧作用域请求自动改写后提交到新版本。

包装层自身维护内部伸展布局，宿主只需按公开合同提供明确尺寸；不可暗依赖独立站点 CSS。交付验收使用已安装包和公开样式，检查编辑区域实际尺寸、可见图形与保存后刷新。写入结果不确定的恢复流程，还须验证显式确认后状态解除、后续保存恢复，以及确认前产生的新草稿不被云端旧内容覆盖。

MA-V 目前实际向组件传 `context/fileClient/conversation`。SDK 可选的 `providerClient` 不等于宿主一定注入；`registerBeforeLeave` 和画布 `transport` 不是该宿主已保证的 props。包装层从已有公共配置/接口适配必需能力；缺口写明，不要求修改他的源码。

### 7.2 三个独立登记动作

| 层 | 安装/登记什么 | 谁做 |
| --- | --- | --- |
| 代码 | npm surface/包装层进入宿主构建 registry，命名导出与版本可解析 | 交付方提供包；宿主维护者按既有机制安装 |
| 目录 | MA 应用 manifest 发布，Provider 地址、动作和权限可发现 | 交付方给 manifest；基座正式机制登记 |
| 业务 | 创建实例、初始化 Provider 数据、关联会话、打开标签 | 基座与 Provider 按约定流程；不让 read 隐式变成 write |

`POST /api/apps/register` 是我们的画布注册，不是 MA 后端的登记 API。npm publish 也不是正式应用发布。当前没有核实 MA 发布 API 时，只交付登记文件和验证结果，不发明端点或直接写表。

### 7.3 MA manifest/Provider 交付要点

- `frontend.moduleId/exportName` 与实际 registry 相同；manifest、后端 `currentVersion`、实例 `applicationVersion` 与包装层的兼容版本对齐。依赖的 surface 可有自己的版本，记录在 BOM，不能机械要求所有 npm 包版本都相同。
- `provider.baseUrl` 是完整可达 URL；Protocol 版本是字符串 `'1.0'`。动作有精确 schema、effect、权限；不能只给 `operations[].type=object` 就声称模型能可靠构造操作。
- `app_...` / `ai_...` 正式 ID 由基座签发。只在显式模拟模式可生成测试 ID，并与真实目录/会话标签隔离。
- Provider 验证可信调用方、租户和实例，再把固定信封转成业务操作；path/body/action/版本一致。actor/permissions 文本不是签名或身份票据。
- 当前画布、文档和草图的App自有包装层/Provider交付状态见 [交付记录](../../../../docs/four-app-completion-20261022.md)；旧“画布只有loopback”不再描述该交付版本。正式票据、资源桥和宿主仍分别待验，不能因fixture或本地200就直接称staging通过。
- 若部署到函数，必须核对函数执行外壳与 HTTP path/method/body/响应之间的映射；不能默认“函数 executions URL 加业务路径”可直接访问。

### 7.4 外部接入所需的最小输入

| 输入 | 提供/确认方 | 缺失时的处理 |
| --- | --- | --- |
| 目标宿主与SDK版本、实际props、moduleId/exportName及CSS/renderer约束 | 宿主/SDK仓库负责人 | 形成兼容表，独立surface与制品工作可继续，目标宿主验收未通过 |
| 正式manifest schema、发布/登记入口、应用版本与ID签发机制 | 基座仓库负责人 | 交付候选manifest，不自造app_/ai_正式身份或登记API |
| Provider完整地址、协议外壳、网关身份证明及动作授权方式 | 基座与App负责人 | 只做明确标注的fixture兼容测试，不公开开发信任入口 |
| 业务云资源、写者身份、schema/ACL、备份与运行锁 | 资源归属仓库负责人 | 缺配置明确不可用；不借用他人写凭据或静默本地回退 |

负责人及资源查询 [资源目录](platform-resource-catalog.zh-CN.md)。外部待提供项属于可追踪依赖，不要求开发者猜测；只有对应门被阻塞，不应伪造依赖或停止所有可独立完成的业务开发。

## 8. CLI 与 Agent 运行合同

CLI 与 UI 是同一个 App 的两个消费者。我们交付可安装包、版本、Skill、配置清单和最小读写任务；MA 维护者负责在其执行环境安装、授予适当网络与凭据、把实例上下文传进调用。

| 要交付 | 最低要求 |
| --- | --- |
| CLI 包 | 独立 npm/tgz、可执行 bin、固定版本、Node 要求、无源码/workspace 路径依赖；安装不启动另一个后端 |
| 配置 | 服务地址、身份凭据来源、团队/调用者、实例 ID/映射；CLI 收到的本机地址必须从 MA 运行位置验证 |
| 行为 | 机器可读输出、失败非零退出、稳定操作 ID、版本与错误透传；不打印凭据、不自动重试不确定写 |
| Skill | 何时调用、能力发现、读版本、参数示例、回执/readback、冲突/离线恢复；引用安装包的实际命令 |
| 验收 | 干净目录安装且源码不可达仍能运行；连接真实测试服务完成一笔写入和失败路径 |

当前 `canvas-server` 源码已有 `apps list/call/state/bindings/entitlements/audit` 及 `request`，地址为 `CANVAS_SERVER_URL`/`--server-url`，传输 token 为 `CANVAS_AUTH_TOKEN`，本地身份为 `CANVAS_TEAM_ID/CANVAS_USER_ID` 或 flags。**这些身份 header 不是生产委托能力。独立 CLI 包的实际名称、安装命令与发布状态必须由发布清单给出。**

`动作说明进提示词`、`前端关键词预执行`、`MA 真实 tool-call` 分别记录。只有获得执行权限的 MA 自己生成参数并发起调用，且网关/Provider 回执与状态可关联，才报告自主调用通过。

### 8.1 能力发现、画布读取与自主调用的验收

| 验收项 | 必须提供的证据 | 不足以证明通过的情况 |
| --- | --- | --- |
| Agent 发现能力 | 实际 MA 执行环境中可用的工具/Skill、CLI bin 与版本，以及 help/manifest/schema 发现结果 | 开发者终端安装成功；规范包里有 Skill 文件 |
| 读取画布 | 已授权并关联的目标实例，经公开 read/snapshot 合同返回真实版本和可读取的节点/关系/业务引用；引用内容按各自权限读取 | 模型根据聊天历史描述画布；只知道画布名称 |
| 自主调用 | Agent run 内生成目标实例与参数，实际发起工具调用，关联请求、权限检查、回执与状态读回 | 宿主规则预执行动作后交给模型总结；开发者代执行 CLI |
| 自主修改 | 先读原版本，按 schema 条件写入，回执与同实例 UI 一致；冲突、撤权和跨实例请求拒绝 | 模型回答“已修改”；另一个实例出现相似内容 |

结构化画布读取与视觉理解分别验收。节点清单、布局及文本可读取，不代表图片像素、嵌入文档全文或所有私有文件已经进入模型上下文。需要视觉理解时，由获准的导出/资源接口提供实际图像并验证模型输入；未授权实例、文件及未声明字段不可读取。CLI 和正式工具桥可按宿主能力选用，但验收必须写明实际路径，不能将 Provider 调用称作 CLI 调用。

## 9. 环境、认证与发布

### 9.1 每个 profile 明确三种地址

| 地址 | 从哪一端可达 | 检查 |
| --- | --- | --- |
| 独立 Web/浏览器 API/资源 URL | 用户浏览器 | Origin、登录态、CORS、CSS/字体/图片、上传/下载/SSE |
| Provider 服务 URL | 基座服务/网关 | 解析、TLS、路由外壳、可信调用方认证、超时 |
| CLI 服务 URL | MA 执行环境 | 包安装、网络访问、身份委托、实例映射 |

`127.0.0.1` 在远端容器中指该容器自身。禁止把开发者目录、固定端口或代理 fixture 写入生产包。构建变量是否可在部署时修改要写清楚，不能声称静态 JS 总能读服务端环境变量。

profile 至少区分 local 独立运行、local 宿主联调、staging。生产不静默降级到本地文件库或 `local/local`；存储缺失应启动失败/503。Appwrite 单写者限制、持久队列卷、备份和重启恢复属于部署合同。

首次部署必须交付完整的私有 schema、索引、桶策略与适用的 namespace 初始化入口；不要只给资源 ID、或引用一个仅在其他开发者检出中存在的脚本。预置工具先提供无云端/凭据 I/O 的计划，再将只读核查与显式创建分开。既有归属、权限或 schema 不匹配时拒绝，不通过放宽 ACL、改写旧开发数据或抢占写锁完成初始化；属性和索引实际可用后才允许进入运行验收。本仓工具见[私有存储初始化交付](../../../../deployment/private-storage-bootstrap.zh-CN.md)。

### 9.2 认证不是显隐

显隐表/卡种 grant 控制能力可用范围，不能替代用户认证、团队成员资格或资源授权。`platform` 范围不代表资产公开。服务端必须独立拒绝绕过菜单的直接请求；身份缓存缺失不得新建信任。SSO、传输 token、委托凭证、actor ID 分开说明。

开发者访问按 [资源目录与审批规则](platform-resource-catalog.zh-CN.md) 执行：仓库负责人审批所属资源，跨仓共享由资源归属方审批。开发资源可能存在已登录用户可读的桶级授权；具体资源及验证日期直接列于本包资源目录，不推广为生产全库可读。通用服务 token 不是只读 token；开发者不得为查看字段运行初始化或修改 ACL，写入联调使用获准的隔离资源。

### 9.3 包发布的最低交付

公司内交付使用经确认的快手内网 registry 和 scope 权限；本仓 `.npmrc` 当前已为 `@ks-designai` 和 `@ks-kp` 配置内网地址；**不能据此推断其他 scope 会自动发到内网**。最新实际包名/固定版本及状态见 [仓库README](../../../../README.md)。发布任务明确 `publishConfig.registry`/发布参数、包名所有权和固定版本，不把凭据写进包。

交付清单至少列：surface、宿主包装层（独立包或与 surface 同包）、可选卡包/纯服务端入口、CLI、Skill、MA manifest、后端部署版本、schema/协议版本、已测 peer 版本、包完整性摘要、证据和限制。版本锁定并允许回滚；数据迁移另外写兼容策略。不要将已有 npm 版本原地替换。

界面运行依赖的自有资产（Worker、字体、样式、媒体处理模块等）必须随固定制品交付，并在实际消费宿主中验证加载，不依赖源码检出、临时地址或宿主碰巧存在的同名文件。

后端镜像须标明目标 OS/CPU 架构，并在该架构实际运行原生依赖、Worker、静态资源与启停检查。冻结清单记录镜像 ID、包摘要和运行输入摘要；核对镜像内运行文件与已验源码/构建产物一致后交付。另一架构或较早镜像的成功不自动覆盖当前制品。

原件验收以上传前后字节哈希相等为准，不能用重新编码图片代替原件保留。完整文件和分块上传是不同的传输 profile，须按实际平台合同分别验证计数、字节与权限；不在结果不确定后偷偷切换方式。资源配置变更应显式保留安全字段，并读回完整策略，不能假设省略字段会保持原值。

模型的产品档位与像素尺寸分别声明。`2K`、`4K` 等标签若按模型或比例映射到不同尺寸，公开合同和界面须明确说明；验收核对请求的模型/比例/档位与实际解码宽高，不能对所有模型套用同一个尺寸断言，也不能插值放大后宣称模型原生输出达到目标。


### 9.4 首次上线、npm 提交与后续更新

完整操作见 [App 发布、更新与 npm 流程](app-release-and-npm.zh-CN.md)。surface/包装层与卡包按 npm 组件包交付，CLI 是独立工具包；后端、云资源、正式应用登记和消费宿主各自发布。先验最终 tgz，再上传确切字节，从 registry 下载与安装读回；消费方固定版本并重新构建，不能仅发 npm 就称所有宿主已更新。

每个 App 填写自己的平台/流水线、包与服务版本、正式登记/旧实例兼容、schema 迁移和回滚操作单。生产发布后由接收方确认运行版本和关键业务结果；合同须记录维护人、健康/告警、任务追踪、适用费用/配额、备份恢复及下线的数据处理规则，未配置项列缺口。当前四 App 的单写者部署先停旧服务再启新版；新架构若采用其他并发部署方式须另验。PDE 静态部署不能代替业务后端或 MA 登记。

| D 卡片互联 | 安装卡包、登记服务端 kind、建立绑定、同实例深编辑/同步 | N/A 或记录冲突，不复制正文规避同步 |

只改文档时检查引用、语义和可执行例子；改代码时按所在仓要求安装/guard/typecheck/包级测试和构建，再做真实运行。使用实际 package scripts，不照抄另一仓的根 build/test。全仓已有失败必须记录具体原因，不算新能力通过，也不顺手修无关模块。

## 11. 验收门与证据要求

| 门 | 通过信号 | 不能代替它的证据 |
| --- | --- | --- |
| 独立 App | 独立壳完成业务，刷新/重启仍在，版本冲突有保护 | 只有组件截图或 HTTP 200 |
| 卡片互联 | 同一绑定双向读写，复制隔离，归档/旧回调正确 | 打开一个长得相同的新文档 |
| 可安装 | tarball 干净安装，类型/CSS/运行均通过，无外部源码依赖 | monorepo workspace 或软链可跑 |
| 模拟宿主 | 未改宿主，明确 fixture，真实组件/本地服务，刷新恢复 | 云端正式注册、生产安全、多租户已通过 |
| 正式接入 | 正式目录→实例→会话→打开→认证调用→持久化 | 本地模拟菜单出现 |
| Agent | run/tool-call→网关→Provider→回执→同实例 UI/readback | 前端先执行、CLI 人工写入后模型复述 |
| staging | 同一交付版本、远端网络/认证/存储、重开/权限/失败验收 | 本机地址换成 staging 字符串 |

每个适用门都做：正常写、重放、旧版本409、缺基线428（适用时）、断网/超时、不存在实例/动作、未授权读写、A/B切换、刷新/重启。身份隔离需真实已验证身份；改 header 的开发测试不能冒充生产授权验收。

构建产物、SSR、单元测试或 HTTP 断言不代替真实浏览器验收；有界面能力的功能须在目标浏览器完成一次真实操作并刷新/重启读回，才计为页面级通过。

证据至少含：commit/包版本/profile、命令/操作、测试时间、专用实例、前后版本、稳定操作ID、回执/错误、读回断言、UI截图（适用时）、限制与复现。不得含 token/cookie/私钥。文档与测试用语一致，不使用“完美注册”“全合规”替代逐门结果。

### 11.1 基于实际故障的回归验证

四App联调新增的JSON序列化、持久化失败、身份快照、凭据请求和制品字节约束集中见 [统一交付增补](unified-app-delivery.zh-CN.md)，具体证据与增删判断见 [规范审计](../../../../docs/app-development-standards-audit.zh-CN.md)。按对应能力补验，不为每个App复制一套新接口。

[草图接入案例](sketch-integration-cases.zh-CN.md)逐项标注已有合同和本次新增细节。开发有云端深编辑的App时，按适用范围检查：绑定是否唯一；长ID/索引是否兼容平台；所有入口是否共用写授权和实例并发保护；不确定回执能否恢复；未保存缓存是否按可信身份隔离；导出是否再次鉴权；发布包是否从registry仓外验证。历史通过只证明记录中的版本/profile。

## 13. 新 App 的首条完整业务链路

首次开发先完成一条可验收的纵向链路，再扩展功能。以含正文与图片附件的业务 App 为例：

1. 在合同中明确正文/附件的权威服务，登记仓库负责人及资源审批归属；使用已授权的测试 project/database/bucket 与 namespace。
2. 交付 schema 预置与配置校验；以真实认证作用域创建实例，记录返回的业务身份，不能从路径或名称猜实例。
3. 读取内容和当前版本，提交携带原基线与稳定幂等键的修改，取得回执，再读回正文和附件字节。
4. 关闭服务，使用空缓存重启，验证实例、文件、回执/未完成任务仍可恢复；旧版本、同键异参、跨作用域和撤权请求拒绝。
5. 独立壳与嵌入式 surface 使用同一服务完成相同任务；从卡片打开时定位原绑定，复制资产时创建独立身份。
6. 若有异步处理，验证成功/失败/取消、结果不确定时的回执查询、目标变化后的回填保护；正常路径和受控失败路径均须有证据。
7. 从固定制品在仓外干净安装组件和CLI，验证CSS、Worker、字体/图片、实际读写及刷新；不能依赖原仓源码或软链。
8. 接入目标宿主并完成正式登记/认证链路；Agent验收关联真实run/tool-call、网关请求、回执、版本和同实例UI。外部条件未提供时保留已完成独立链路和具体依赖。

本例规定验证顺序，不定义新的平台 actionId 或业务字段。具体命令从已交付 CLI 的 help/manifest/schema 获取，并登记在 App 合同。纯卡包复用平台的持久化、动作与回执，不重复建设上述后端。

## 14. 内置 PDE Agent 的适用方式

PDE Agent 工具与参考资料随规范内置，入口见 [PDE 适配说明](pde-agent-integration.zh-CN.md)。按实际任务选择初始化、Appwrite、静态托管、OneSQL 或设计资料，不因引用工具就重建 App 或改变目标仓技术栈。静态站发布不部署业务 Node 服务，也不替代 DA/MA 应用登记、Provider 认证或 Agent 工具安装。

## 15. 规范维护与兼容变更

规范随架构与合同演进维护；代码修改若影响协议、数据权威、权限、持久化、部署或制品，必须在同一交付中评估规范影响。

| 变化 | 应更新的文档 | 不应直接推广的内容 |
| --- | --- | --- |
| 共同责任、适用范围或交付阶段变化 | 本白皮书、Skill入口及APP_CONTRACT模板 | 当次未完成状态、临时方案 |
| 对外字段、错误、版本、幂等或身份合同变化 | 对应专项合同、App合同、兼容/迁移说明 | 未获宿主承诺的接口 |
| 仓库、负责人、资源、用途或审批变化 | 资源目录及受影响的 App 合同 | 本机临时端口与未经核对的权限 |
| 实际故障揭示可重复的边界缺口 | 先记证据与案例，再补适用合同和验收点 | 自动化观察不足、单一业务算法 |
| 实现修复但合同已明确 | App问题记录和回归证据，必要时补案例 | 为每个bug重复增加全局禁令 |

变更记录包含：问题与来源、适用范围、增/改/删决定、兼容影响、验证方式、维护负责人和日期。删除或改名之前检查现有引用，过时示例保留历史标记或提供迁移指针。

规范提交前执行链接/标题、代码块、模板覆盖和示例审查；功能变化仍须单独运行实际测试。采用新字段/授权/存储约定的App更新自己的合同与兼容表，不由文档自动迁移数据或修改ACL。业务状态保存在执行记录，不以白皮书中存在条款证明实现完成。

规范维护归画布平台仓库负责人；宿主/SDK合同变化由其仓库负责人确认；资源访问审批按资源归属仓库执行。发现影响规范的问题时，人与AI均应主动形成规范影响说明并同步对应文档，无需等到下一次集中整理。

维护本规范仓时运行只读检查：

```sh
pnpm exec tsx scripts/verify-app-standard-docs.ts
```

需要同时核对附加交付文档时，可重复传入 `--extra-md /absolute/path/to/index.md`。此工具检查本规范包的本地链接/标题及代码围栏，不代替语义审查、真实开发或功能验收。
